# Local task control API contract

Only binds 127.0.0.1. Same origin JSON APIs. All JSON errors: `{ error: string }`.

- `GET /api/bootstrap` → Bootstrap from shared/types.ts. Mock providers available; real Hermes, Claude Agent SDK and Codex are available only when explicitly configured at server startup. Availability means configured, not successful provider verification. Runtime labels describe this service, not an inferred Mac/Windows device or remote connection.
- `GET /api/sessions` → `{ sessions: SessionSummary[] }`, newest updated first.
- `POST /api/sessions` body `{ adapterId, title? }` → `{ session: Session }`, status 201. Reject unavailable/unknown adapter.
- `GET /api/sessions/:id` → `{ session }`.
- `GET /api/sessions/:id/events` → SSE `event: snapshot`, `data: { session }`; initial snapshot immediately; subsequent task changes and chunks. Native EventSource auto reconnect refreshes snapshot. Heartbeat comments.
- `POST /api/sessions/:id/tasks` body `{ prompt, mode?: 'chat' | 'approval-demo', idempotencyKey? }` → `{ task }`, 202. Prompt 1–8000 chars. An optional key is 16–100 ASCII letters, digits, `_`, or `-`, scoped to this local session. The same key and normalized prompt/mode return the original task without executing again, including after completion or restart; a different payload with that key returns 409. A missing key retains the original behavior. Only one active task (queued/running/cancelling/awaiting_approval) per session, conflict 409. Real adapters reject approval-demo before creating any task or message. The selected conversation keeps its existing full-session API; the task activity view uses the separate metadata endpoints below.
- `POST /api/tasks/:id/cancel` body `{}` → `{ task }`. Abort queued/running/waiting only; other transitions conflict 409. Running real CLI tasks first enter cancelling and hold the session lock until process termination is confirmed; an unconfirmed native-driver stop becomes unknown and blocks real execution across restarts. Legacy exec retains failed + stopUnconfirmed quarantine semantics.
- `POST /api/tasks/:id/approve` body `{}` → `{ task }`, 202. Only awaiting_approval; continue a clearly labeled local simulated action. Never send messages or execute commands.

Default mocks produce deterministic Chinese simulated replies with streaming and contextual turn count. `/fail` intentionally returns a failed task for demo and verification. `approval-demo` pauses before executing a simulated local plan, explicit approve/cancel required. Persist sessions/messages/tasks in SQLite; interrupted mock and legacy exec work follows its original startup policy, whereas Hermes, Claude and Codex App Server preserve native uncertainty and require exact evidence before a terminal update. Store DB under `.data/` (gitignored).

## Execution boundary

The task engine routes through an internally registered `EngineDriver` per adapter, retaining legacy Codex compatibility. At most one real task across all sessions may be queued/running/awaiting approval/cancelling; an unknown result or unconfirmed stop blocks new real work. Mocks do not consume this execution slot. Conflicting real submissions are rejected with 409 before creating a task. Existing idempotency keys still return the original task before availability/concurrency checks.

Hermes (`hermes`, kind `http`) is a separately enabled loopback driver. `Session.engineBinding` discriminates the provider; Hermes bindings contain its actual API session ID and protocol version. `Task.nativeTurnId` contains the accepted run ID and is persisted before the first status query. Recovery can inspect this exact run even when the first session-binding reply was lost. It never guesses an ID, creates another run, or resolves upstream uncertainty automatically. Missing run IDs remain quarantined. See [Hermes integration](hermes-integration.md) for supported native approval shapes and remaining verification gates.

Hermes, Claude and Codex App Server use the same native approval and recovery routes. Hermes tools expose `kind: tool` and only the single-use decisions supported by the current native prompt. Receipt `already_resolved` cannot prove that this caller's approval was applied, so it becomes unknown. Cancelling stays visible until native terminal evidence; request acknowledgement alone is insufficient. RelayDesk does not impose an OS sandbox or change the Hermes tool policy.

The legacy exec adapter (`codex`) uses a fixed local executable, workspace, model and environment supplied only by the server operator. HTTP bodies cannot override them. Each task starts an ephemeral process, submits session text history through stdin, and publishes completed assistant messages through SSE. Only one real task runs at a time across all sessions; concurrent real submissions are rejected with 409 before spawning or admitting another task. CLI diagnostic text never enters the public error response. Existing real sessions remain readable after disabling Codex, but cannot submit tasks.

Interrupted legacy exec tasks become failed with `stopUnconfirmed: true` on restart; a restart cannot prove an old process is gone. This marker keeps real execution quarantined across subsequent restarts. Only the local startup environment may acknowledge a manual process check through `RELAYDESK_CODEX_ACK_INTERRUPTED=1`, never an HTTP request. A storage write failure stops active execution and makes subsequent mutation requests return 503 until storage is repaired and the service restarted. Any in-memory failure snapshot explicitly indicates it may not have been saved.

Frontend: React + TypeScript + CSS. User-facing language Chinese, RelayDesk brand. Mobile friendly navigation. Initial no fake seeded user sessions. Empty state prompt cards, mock labels prominent, errors visible. Adapter selector available when creating a new conversation, adapters immutable per conversation. Task list/current status and approval cards. Channel view shows all planned connectors honestly.

## Native Codex App Server

Adapter ID `codex-app-server` is independent of the legacy `codex` exec adapter. The server operator enables the exact supported official CLI; no HTTP argument can change the executable, model, working directory, sandbox, environment access or protocol method. The browser has no generic JSON-RPC proxy.

`Session.engineBinding` saves the official thread ID, driver version and fixed workspace. `Task.nativeTurnId` identifies the exact native turn. The binding is committed before `turn/start`; the turn ID is committed on receipt. Each subsequent task resumes that thread and sends only the new prompt. Native assistant messages are upserted by task and item ID; completed item text replaces the accumulated text. Repeated equal text deltas are not discarded. SSE reconnect sends the current full persisted snapshot, not a replay of executable events.

- `POST /api/tasks/:id/native-approvals/:approvalId` body `{ decision: 'accept' | 'decline' | 'cancel' }` → `{ session }`. Uses an immutable local request ID bound to native thread, turn, item and typed JSON-RPC ID. Only pending, unexpired requests and their advertised single-use decisions are accepted. Intent is saved before sending; an uncertain write is never retried. Duplicate, stale or wrong-task requests return 409. This route is separate from mock approval.
- `POST /api/sessions/:id/recover` body `{}` → `{ session }`. Reads only the bound native thread and exact persisted turn after an interrupted execution. It never sends another prompt. Confirmed terminal evidence updates messages and status; otherwise the task stays `unknown`. Missing turn identity cannot be inferred from a different historical turn.

Native cancellation first becomes `cancelling`. `turn/interrupt` acknowledgement alone is insufficient: only `turn/completed` confirms `completed`, `cancelled` or `failed`. Restart or uncertain connection outcomes become `unknown` with `stopUnconfirmed`. Native pending approvals become unknown and cannot be reused after restart. A session with an unknown result cannot submit another task; the legacy environment acknowledgement cannot clear native uncertainty. The implementation runs a private stdio process per turn/recovery and resumes official persisted threads; it does not install a system daemon.

### Native task activity

These read-only endpoints project `codex-app-server`, `hermes` and `claude` tasks, distinguished by actual provider. They do not use synthetic inbox projects. Before a workspace binding exists, `project` is null (ungrouped); Hermes has no RelayDesk workspace binding. Codex / Claude workspace labels use an opaque identifier and a fixed provider label, never an absolute path. Task titles use the local task ID, not the prompt or conversation title.

- `GET /api/task-feed?scope=active|history|all&limit=30&cursor=...` → `{ feed: TaskFeedPage }`. `scope` defaults to `active`; `limit` is an integer from 1 to 50. Active includes queued, running, awaiting approval, cancelling and unknown; history includes completed, cancelled and failed. The page includes `total`, `activeCount`, `historyCount`, `truncated`, `nextCursor`, `generatedAt` and `revision`. Tasks sort by immutable `createdAt` then task ID, both descending. The opaque cursor binds that ordering position and scope; invalid, altered or mismatched cursors return 400. Activity updates do not reorder history. This is a current-state page, not a transaction held open across subsequent pages: clients merge by task ID and refresh the first page for new tasks or status changes.
- `GET /api/task-feed/events?scope=active|history|all&limit=30` → SSE `event: snapshot`, `id: <revision>`, `data: { feed: TaskFeedPage }`. Supports the same scope/page-size bounds but no cursor. Every connection immediately receives a fresh first-page snapshot, regardless of `Last-Event-ID`; no prompt, approval or cancellation is replayed. Changes are coalesced over 100 ms, so intermediate states can be absent from a snapshot. Heartbeat comments are sent every 15 seconds. At most 32 feed streams are open at once; excess connections return 429. A stream whose pending output exceeds 256 KiB is disconnected and must reconnect for a fresh snapshot.
- `GET /api/task-feed/:taskId/activity?before=<sequence>&limit=50` → `{ activity: TaskActivityPage }`. Hermes, Claude and Codex App Server tasks only; mock and legacy exec IDs return 404. `limit` is an integer from 1 to 100. Entries are newest first and contain only `seq`, `at`, `kind`, and a fixed server-generated `label`. `nextBefore` pages backward within this task. An invalid sequence or one beyond `latestSeq + 1` returns 400. At most 200 entries are retained; `retainedFrom` and `truncated` explicitly identify missing older activity. Consecutive equal categories coalesce and refresh their timestamp, so this is a bounded activity summary rather than a complete protocol audit log. Old tasks without recorded activity receive a fixed status fallback in the feed and an empty activity page; old error strings and event details are never imported as activity labels.

Unknown/duplicate query parameters, non-integer limits and stream cursors are rejected. These routes retain the same loopback Host/Origin restrictions as the rest of the API. They expose no general RPC method, command, executable, model or working-directory input.

`TaskFeedItem` includes task/session IDs, provider, status, creation/start/end observation times, elapsed milliseconds, last activity time, current activity, `stopUnconfirmed`, and pending approval metadata. `pendingApprovalCount` reports the total; at most 10 pending/responding entries include ID, kind, status and creation/expiry times. Review content and allowed decisions remain in the existing explicitly opened conversation's immutable native approval view. The task feed is not an approval preview and cannot authorize an operation. Existing approval, cancellation and read-only recovery routes remain unchanged.

Provider receipts drive activity categories. Hermes currently projects lifecycle and polling state; it does not expose a complete tool-event stream. For Codex App Server, real native notifications drive activity categories. Connecting and thread-ready reflect local lifecycle; turn-started, reasoning, replying, command and file-change categories are emitted only for the bound native turn. Turn activity is held until the `turn/start` response verifies the turn ID. Reasoning is represented only by the high-level label `正在处理请求`; hidden reasoning text is neither stored nor published. Prompts, assistant text, commands, stdout/stderr, file paths/diffs, configuration and raw provider errors are absent from activity storage and these endpoints. Labels are reconstructed from a fixed allowlist even for older stored rows.

The `revision` is `<server-epoch-UUID>:<monotonic-counter>`. The counter advances on native session changes; a restart creates a new epoch. Within an epoch, clients must not overwrite a newer SSE snapshot with an older GET response. Reconnect is a fresh observation, not evidence that a task resumed. A quiet activity timestamp never implies failure. `elapsedMs` is the locally observed interval starting at first running state (or creation for queued/older tasks), frozen at an observed terminal. Unknown states have no confirmed end time; recovery records the time terminal evidence was obtained. The interval can include disconnection and recovery time and is not exact provider execution or billing duration.

This is a trusted local operator interface. Host/Origin checks do not constitute remote user authentication; VPS authentication, pairing and remote approval identity remain a later stage.

## Claude Agent SDK

Adapter ID `claude`, kind `cli`, is independently enabled by the local operator. It uses official SDK 0.3.309 / CLI 2.1.309, with the SDK bundled native CLI as default and a fixed `.data/claude-native-workspace`. Optional executable/model/environment configuration is startup-only; no HTTP body can override it. Desktop is not used as an API or treated as proof of CLI authentication. Account checks require first-party subscription authentication and no API-key source before admitting the prompt; no API key, bearer or cloud-provider fallback is used.

`Session.engineBinding` contains `{ driverId: 'claude', threadId, workspace, version }`, with the actual SDK session ID. `Task.nativeTurnId` stores the exact SDK user-message UUID before sending; a result must match that identity and the bound SDK session, with zero subprocess exit evidence before completed can be confirmed. Tasks resume only their own stored session and submit only the new prompt. No Desktop conversation is attached by title or copied from its private state.

Each turn starts an SDK query on demand, consumes its matching result, and closes the query / subprocess. Default tools are empty. The optional local environment profile enables only supported, individually approved Read / Glob / Grep calls. Bash is denied because Windows shell choice, cwd conversion and descendant-stop behavior are unverified; Edit / Write are also denied until complete immutable diff handling exists. Generic permission bypass, permanent approval, bulk approval, and browser-supplied commands or RPC methods are not exposed. Fixed cwd and tool restrictions do not constitute an OS sandbox; managed organization hooks remain a separate local verification boundary.

The existing native approval route binds the decision to the task, immutable SDK permission callback request and exact operation preview. Only supported single-use decisions are accepted. The mock approval route cannot resolve SDK callbacks. Cancellation stays `cancelling` until matching result and subprocess exit evidence can establish the outcome; uncertain result or exit remains `unknown`, blocking all new real tasks.

`POST /api/sessions/:id/recover` validates the saved session/user-message identities and reads only the matching SDK session messages. It does not claim that transcript entries identify a terminal result for that UUID. It does not resume inference or submit another prompt. Current SDK history is not an authoritative terminal receipt, so recovery remains `unknown` even if an assistant reply is present. It cannot clear quarantine, infer success from the last message, or be overridden by the legacy Codex startup ACK. Durable terminal receipts and a controlled manual recovery process remain future work.

Configuration, official authentication references, subscription/billing limits, memory-measurement boundaries and real verification gates are in [Claude integration](claude-integration.md). SDK/CLI installation and configured availability are not real-model verification.
## Synthetic work inbox

Types are in `shared/inbox.ts`. This feature has no WeChat connection, external sender, model call, or command execution. Project summaries and source links are fixed synthetic examples marked `deterministic-demo`; no incoming message is an instruction to an execution adapter.

Threads and source messages use `projectIds` arrays: a conversation can contain messages for several projects, and a single source can be associated with more than one project. Project requirements, deadlines, questions, and `todos` retain source evidence. These are fixed confirmed demo associations, not AI classification. The current UI displays requirements, deadlines, and questions; no classification-confirmation editor or todo interaction is implemented. Future uncertain classification suggestions must be confirmed separately before becoming project records and never grant send permission.

- `GET /api/inbox` → `{ inbox: InboxSnapshot }`. Initially empty; returns projects, stable threads, source messages, and reply states. The UI polls this read-only endpoint while the inbox is open.
- `POST /api/inbox/demo` body `{}` → `{ inbox }`, 200. Loads two invented projects and three threads, including distinct contacts with the same display name. Repeated loading preserves the existing demo and delivery records. This is fixture-load deduplication, not a verified live channel event receiver.
- `POST /api/inbox/replies` body `{ threadId, sourceMessageId, content, idempotencyKey, demoOutcome }` → `{ reply: InboxReply }`, 201 for a new immutable draft, 200 for an existing equivalent reply. `content` is 1–4000 characters, preserved exactly; `idempotencyKey` is 16–100 ASCII letters, digits, `_`, or `-`; `demoOutcome` is `succeeded`, `failed`, or `unknown`. Preparing a draft never sends it. The server validates that the source belongs to the selected thread and derives the account, native thread ID, and target title from stored data.
- `POST /api/inbox/replies/:id/send` body `{ intent: 'send-reply', confirmReview?: boolean }` → `{ reply }`, 202 when the mock delivery starts, 200 for a reply already submitted. This separate request expresses send intent for the immutable reply ID. Source risk flags or demo keyword rules require `confirmReview: true`; these rules are not complete sensitive-data detection. The route does not accept target or content overrides.

The same idempotency key with different bound content, source, or demo outcome returns 409. An equivalent account/thread/source/content/outcome with another key resolves to the existing reply and records the key alias. A submitted reply is never delivered again. Any reply for the same source already `sending` or `unknown` blocks another send with 409, including changed content or a new key. A failed delivery remains final for that reply; there is no automatic retry. These are conservative local demo semantics, not proof of a real provider's delivery behavior.

`draft → sending → succeeded | failed | unknown`. Authorization and `sending` are saved before the mock sender runs. A success receipt is explicitly prefixed `mock-`. Service restart converts interrupted `sending` to `unknown`. The API offers no retry or unlock for unknown delivery. A save failure returns 503 and freezes inbox writes; an in-memory unknown state says it may not have been saved. Read-only polling can inspect status without sending again.

Inbox data uses a separate SQLite table in the same local database file. Existing AI chat sessions remain separate. All inbox mutations use the same Host, Origin, JSON body size, content-type, and unknown-field checks as chat mutations. The service remains loopback-only and is not a remote authenticated gateway.
