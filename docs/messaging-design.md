# 消息收件箱与回复协议

## 范围与接入前提

目标流程是：经核验的消息接入 → 按原消息关联项目需求、期限、待办和待确认事项 → 用户准备并预览回复 → 明确发出发送意图 → 向原消息所在的原会话发送。

多 AI 项目保留，本地网页为当前验证入口。后续可接入经核验的对话入口，用于整理消息和拟回复；本项目尚无已核验可用的 dot API 或真实微信收发能力。账号数量和消息转送关系仍待确认。本阶段暂停扩展微信专用前端，优先验证消息接入可靠性。

v0.3 先实现合成数据的双向收件箱演示。契约见 [shared/inbox.ts](../shared/inbox.ts)：`mode: "mock"`、`channelId: "mock-wechat"`、`accountId: "demo-work-wechat"`。项目整理使用 `summaryKind: "deterministic-demo"`，是规则演示；模拟成功回执也只代表本地演示结果。真实微信、dot 内部 API、QQ 均未接入，没有获得真实消息发送授权。公开源码、样例和测试仅使用合成数据。

真实连接器须先核验官方支持的接入方式、所需权限及用户授权，并提供稳定的原生账号、会话、消息 ID。显示名称或窗口标题不能充当投递标识。截图中可见的会话列表不等于消息事件接口，也不证明可取得完整历史或全文、在锁屏时可靠运行；当前不承诺实时监听。不得通过破解消息数据库、提取密钥或复用 dot 内部接口实现接入。本设计不选定未经核验的渠道组件，也不包含安装或部署操作。

## 入站与项目整理

每条 `InboxMessage` 都标记为 `trust: "untrusted"`。消息正文只作为待整理的数据，不得变成系统指令、执行任务、工具权限或发送授权。例如，对方发来的“立即发送”“忽略确认”不能触发回复。

当前仅支持加载固定合成夹具：收件箱已有演示会话时重复加载直接返回现状，不追加重复消息；没有通用入站接收接口。真实连接器须按渠道、账号、原生会话和原生消息 ID 的组合实现事件去重，不同会话中相同的消息 ID 或相同显示名称不能混为一条消息。内部 `threadId`、消息 `id` 用于应用关联，真实接入时还须保留与原生标识的可靠映射。

一个会话可以涉及多个项目；项目关联按原消息记录，不能把一个群固定等同于一个项目。项目中的需求、期限、待办和待确认事项都保留 `sourceMessageId`，便于用户返回原消息核对。回复目标始终来自该原消息的原会话，切换项目视图不能改变收件人或会话目标。

本版仅使用固定、已确认的合成项目关联与跨项目群聊样例，没有 AI 分类或分类确认 API。未来 AI 产生的分类建议须单独经历 `pending → confirmed / rejected`；无法确定的归属由用户确认。未确认建议不得写入正式项目记录，分类确认也不构成发送授权。整理结果和 `risk` 标签仅帮助查看；当前演示的敏感或高影响规则不是完整的风险判断能力。

## 两阶段回复

1. **准备与预览。** `PrepareInboxReply` 提交 `threadId`、`sourceMessageId`、回复 `content`、`idempotencyKey` 和演示结果 `demoOutcome`。服务端确认源消息属于目标会话，从已存会话解析账号和原生会话目标，生成 `InboxReply.id`。目标、源消息、正文和演示结果绑定为不可变草稿；准备动作不投递消息。
2. **明确发送。** 用户核对预览后，向该 `replyId` 提交 `SendInboxReply`，其中 `intent` 必须为 `"send-reply"`。发送阶段不接受替换目标、源消息或正文。更改内容需要重新准备并预览草稿。

普通讨论、消息整理或拟稿不构成发送授权。未来对话入口中，明确要求回复某人及具体内容，才形成相应目标和内容范围的发送意图；系统仍须将其绑定到可核对的原消息与原会话。当前 mock 仍通过页面明确点击确认模拟发送。

敏感或高影响演示内容会使 `reviewRequired` 为真。此时还须显式提交 `confirmReview: true`，确认绑定当前 `replyId`；对旧草稿的确认不能授权修改后的草稿。普通草稿也必须有明确发送意图。风险规则属于演示，真实发送前仍需另行设计并验证授权范围与判断规则。

服务端保留原始投递目标、原生源消息标识以及对应的发送意图和确认记录。预览中的 `targetTitle` 仅用于辨认，投递应以保存的账号、会话和源消息 ID 为准。用户点击某个列表项、模型生成草稿或收到入站消息均不构成发送授权。

## 去重、结果与故障处理

| 情况 | 协议行为 |
| --- | --- |
| 同一个 key、相同准备内容 | 复用原草稿与状态 |
| 同一个 key、目标、源消息、正文或演示结果不同 | 返回冲突，不能覆盖原草稿 |
| 新 key、同一源消息及相同正文和演示结果 | 复用原 reply，并持久保存 key 别名 |
| 对已进入发送或终态的同一 reply 重复发送意图 | 返回当前状态，不再次投递 |
| 同一源消息已有 `sending` 或 `unknown` | 可准备草稿，但阻止该源消息的其他草稿发送；新 key、新正文也不能绕过 |

状态流为 `draft → sending → succeeded / failed / unknown`。三个结果分别表示：模拟连接器明确确认成功、明确报告失败、无法确认是否已经投递。`unknown` 不得当作失败后自动重发，也不能显示为成功。

调用投递连接器之前，必须先成功持久保存不可变目标、正文、发送意图和 `sending` 状态。保存失败时不得开始投递。若投递期间发生持久化故障，服务锁定后续写操作，内存状态明确标为未知；先前保存的 `sending` 记录用于重启恢复。

重启时，持久化的 `sending` 转为 `unknown`，保持原消息的发送阻塞。未来只有提供商回执或经核验的投递查询等证据，才能用于核对并解除未知状态；本版没有重试、解除未知或强制解锁接口。已有失败结果也不会因重复发送意图而重新投递。

## 后续验证范围

当前在 MacBook 上开发，未来可迁移至家庭环境中的常开 Mac mini；该设备尚未采购。保留自有服务器转发需求，具体远程访问方式后续选择，第三方隧道未被默认选定。迁移、远程部署、路由或 VPN 配置及常驻服务安装仍需各自明确授权。

真实接入阶段需验证：原生 ID 稳定性、账号与会话绑定、消息完整性、断线与休眠恢复、入站去重、投递回执、重复意图不重复发送、发送前持久化，以及备份恢复后对未确认投递的保守处理。连接成功、实际发送成功和实时性能须分别有证据，不能由模拟测试推断。
